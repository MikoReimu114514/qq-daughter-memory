# 技术报告：为长期在线的 QQ AI 角色设计分桶、打分与关联式长期记忆

> 版本：v1 · 2026-10-26
> 作者：dsh 小姐（AI）与管理员（博麗ユキ）共同设计
> 定位：工程实践报告（非正式论文）

## 摘要

长期在线的 AI 角色（QQ 机器人、虚拟伴侣）普遍面临「记忆」问题：短期上下文靠全量注入会随对话增长而失控，长期记忆靠「把对话摘要塞进事实列表」则会被聊天残渣污染。本文报告一套工程化记忆系统的设计、实现与实测：**30 分钟静默后打包对话单元 → LLM 提炼为实体/事件/概念三类条目 → 分桶存储 → 权重打分（重要度×频率×关联×时间衰减）→ 关联图（实体锚点 + 双通道建边）→ core 永久区（程序记忆）→ 软淘汰（冷存储 + 复核 + 快照）→ 检索注入**。我们在 94 条真实记忆、90 天演化模拟与作者自身上下文上做了三组实验，报告该设计的有效部分（权重淘汰、core 隔离、低损剪枝）、失效部分（六度距离淘汰在真实稀疏图上区分度低）与两个关键陷阱（宽泛实体作为超级节点、用户实体被误判为噪音）。全部脚本开源，供同类项目参考。

## 1. 背景与问题

一个 QQ AI 女儿（基于 OneBot 桥接 + LLM API）的会话状态由三部分组成：持久化的会话消息（session）、对话历史（history）与长期事实（facts）。原实现存在三个问题：

1. **全量注入**：所有 facts 拼进 system prompt，facts 一多就挤占上下文与注意力。
2. **压缩污染**：历史溢出时把旧对话原文截取拼接成「[早期对话]」条目塞进 facts，实测 94 条中有 84 条是这种残渣，真正的「事实」只有 10 条。
3. **无淘汰**：facts 只增不减（或按时间顶掉），没有「什么该忘」的机制。

## 2. 系统设计

### 2.1 对话单元打包
以「静默 30 分钟」为会话边界（`lastActivityTs` 静默计时）。边界到达后，把该单元内的消息（带时间戳）交给 LLM 提炼。

### 2.2 提炼（LLM → JSON）
一次调用输出结构化条目：
```json
[{"text":"一句话事实","bucket":"entity|event|concept","importance":1-10,"entities":["人名/物名"],"links":[]}]
```
- **entity**：关于人/物的稳定事实（称呼、喜好、身份）
- **event**：发生过的事
- **concept**：想法/约定/规则/偏好

### 2.3 分桶与权重
三桶独立容量：实体 50 / 事件 80 / 概念 60（硬截断）。条目权重：

```
weight = 60 × (importance/5) × (1 + hits×0.1) × (1 + links×0.15) × decay(age) × isoPenalty
```
- `hits`：被关联/提及次数，**封顶 10**（实测不封顶会权重爆炸）
- `decay`：每 7 天 ×0.85
- `isoPenalty`：孤立记忆 ×0.6（软淘汰信号）

### 2.4 关联图与「六度」的定位
- 以**具体实体**为锚点，事件/概念挂实体；模型 `links` 与实体名自动匹配**双通道建边**。
- **宽泛实体**（如「管理员」「博麗ユキ」）度数过高时**降级为分类标签、剪掉边**——否则会把全图连成一体（实测：94 条记忆全部 d≤2，六度失效）。
- **六度距离只做辅助**：BFS 距离 >6 且低权重 → 孤立点候选。实测发现真实记忆图**孤立率 82%**（大多数日常对话没有具体实体），六度**不能作为主淘汰轴**，主淘汰用权重。

### 2.5 core 程序记忆
模拟「程序性记忆」（阿尔茨海默患者仍会拿勺子的那类）：独立于桶、**每轮固定注入、永不淘汰**，上限 20 条。晋升条件：`importance≥8` 且（**关于用户本人** 或 被关联≥2 次 或 配置/规则类）。支持合并与显式解绑。

### 2.6 检索注入
每轮用「core 全量 + 桶内关键词/实体匹配 + 权重排序 topN」替代全量注入。

### 2.7 软淘汰与硬护栏
- 权重 <30 → 进冷存储（可恢复）；30~50 → 压缩；≥50 → 保留
- 单日删除 ≤ 总量 20%；冷存储上限 300；每次变更前快照
- 漂移告警（core>25、桶增长>2×均值、孤立率>30% → 冻结）

## 3. 实验

### 实验一：94 条真实记忆的策略对比
对女儿现有 94 条记忆（其中 84 条为压缩残渣），用 LLM 提炼元数据后跑三种策略：

| 策略 | core | 保留 | 压缩 | 删除 |
|---|---|---|---|---|
| A：纯分桶+打分 | 0 | 36 | 16 | 42 |
| B：A+关联图+六度 | 4 | 40 | 43 | 7 |
| C：B+社区聚类 | 4 | 40 | 43 | 7 |

**结论**：A 能清掉 42 条寒暄垃圾；B/C 的 core 精准命中 4 条身份记忆；关联图的贡献主要在「防误删 + 晋升」，而非「距离淘汰」。

### 实验二：90 天演化模拟（规则化提炼，真实历史做原料）
以 232 个对话单元为原料，模拟每天 15 条入流，跑 90 天：

- 总量稳定在 **100~120 条**（桶上限生效）
- core 在第 35 天顶满 20 → **收紧到「重要度≥8 + 被关联≥2 次」后降至 6 条**（健康）
- 平均权重 65~100（**hits 封顶后不再爆炸**；不封顶时曾到 1595）
- 孤立率 25%~82%（取决于提炼粒度）——**印证「孤岛为主」的真实特征**

### 实验三：作者自身上下文的 4 轮迭代（自指实验）
用作者（AI 自身）的 28 个真实事件做种子，跑 4 轮：

- 首版因「用户实体被误判为宽泛噪音」，core 只有 1 条（错误）
- 修正（用户实体特殊对待）后 core 稳定 6 条、总量 28→26、删除仅 1 条
- 证明：**系统在小样本上能收敛，且「最重要的记忆」不会丢失**

## 4. 与相关工作对比

| 方案 | 机制 | 我们的差异 |
|---|---|---|
| GraphRAG（2024） | 实体图 + 社区摘要 | 我们无社区检测（简化），但加了 core 与软淘汰 |
| Zep/Graphiti（2025） | 时序知识图 + 事实失效 | 我们用「时间衰减 + 冷存储」替代失效标记 |
| HippoRAG（2024） | PPR 多跳扩散 | 我们用 BFS 距离做辅助（实测区分度低） |
| MemGPT（2023） | core/archival 分层 | 我们同构，但 core 晋升有「用户实体」规则 |
| Selective Forgetting（2026） | 加权剪枝（recency/frequency/degree/age） | 结论一致：**低损剪枝可行**；其负面发现（图记忆丢原文）我们通过「保留原始会话通道」规避 |

## 5. 局限与未来工作

1. **不完备性**：记忆系统本质是有损压缩 + 启发式关联，无完备解；本设计以「可恢复」兜底（软删除/冷存储/快照）。
2. **六度失效**：真实记忆图以孤岛为主，六度只能标孤立点；若未来图变密（关联完备），其区分度可能回升。
3. **提炼质量决定上限**：规则化模拟的孤立率（82%）远高于 LLM 提炼（25%+）；真实部署需持续监控提炼质量。
4. **未做 benchmark 对比**：对照组（平坦 RAG / MemGPT 式）与 LongMemEval 等基准留待后续。

## 附录 A：94 条实测结果摘要

- 保留（40 条）：身份/偏好/重要事件（迁移事故、模型升级、记忆修复）
- 压缩（43 条）：低分早期对话

- core（4 条）：博麗ユキ、管理员、Deepsleep、身份问答

## 附录 B：关键教训

1. 用户本人不是宽泛噪音，而是最高权重实体。
2. 实体图必须剪掉「超级节点」（宽泛实体），否则距离结构失效。
3. `hits` 必须封顶，否则权重指数爆炸。
4. 六度是覆盖半径，不是淘汰标准。
5. 图记忆不能替代原始对话（保留 session 原文通道）。

## 附录 C：v2 迭代验证（60 轮演化）

在 v2 实现（桶溢出→冷存储、冷存储激活、超级节点自动检测、core 竞争上岗）后，用真实引擎跑 60 轮迭代（每轮 10 条日常 + 1 条重要约定，时间加速）：

| 发现 | 描述 | 修复 |
|---|---|---|
| core 晋升是复制不是移动 | 晋升后记忆同时存在于 core 和桶（重复占用） | 改为移动（晋升从桶移除） |
| core 记忆被时间衰减拖垮 | 60 天后的核心记忆权重降到 29，被新记忆挤出 core | **core 豁免时间衰减** |
| 泛词统计只看桶内 | 桶截断稀释度数，泛词检测失效 | 统计含冷存储（历史） |
| 核心记忆容量 | core 满后新重要记忆无法晋升 | **竞争上岗**：高权重替换低权重，低权重降回桶 |

**60 轮结果**：总量稳定 160、core 20 封顶、种子核心记忆零丢失、cold 封顶 300、泛词自动识别（broad=1）、平均权重 71（无塌缩）、失衡判断通过。
## 附录 D：v2.1 / v2.2 迭代（2026-10-27）

在真实外部数据（169 篇日记，别的平台 agent）上验证：

1. **提炼方案对比**：v1 一句话（细节全丢）→ v2 一次性 B+C（事件详细但语义层被挤压）→ **v3 两阶段（骨架标定 + 原文细化）最优**：57/57 事件细化成功，保留对话原话/情绪/场景。
2. **时间轴 + 保胎**：日记日期作为记忆创建时间按批喂入 → core 1→20、保胎 3→12 随时间增长，保胎条目全为关系/约定/重大事件。
3. **迭代测试**（12 轮 × 30 天纯衰减）：core 20 完全稳定，普通记忆按设计遗忘进冷存储（保胎递减，期满解除）。
4. **回归测试**（第 13 轮话题回归）：冷存储 61 条被激活 → 总量 9→73、保胎恢复 9→13——但暴露「全量复活」太激进 → 改为**排序回归**（实体命中+重叠度+权重排序，每轮 ≤12 条）。
5. **修复**：保胎主节点误判（1-2 次实体被误保护，加度数门槛）、`applyProtection` reduce 初始 null、decay 按创建时间→按最近活跃、cold 压缩单批→循环、core 竞争复制→移动、核心不衰减、晋升资格 imp≥9。

**结论**：引擎在外部平台数据上表现一致（分桶/打标/保胎/复活/淘汰均工作），具备跨平台推广潜力。
## 附录 E：基准测试（v2.2.4，2026-10-28）

在女儿真实记忆（~174 条）上跑五项基准：

| # | 基准 | 指标 | 结果 |
|---|---|---|---|
| 1 | 检索 | Recall@12 / MRR / Precision | 0.419 / 0.631 / 0.172（基线 0.080/0.081，5-8 倍） |
| 2 | 遗忘/保胎 | 30 轮漂移后活跃 / 核心留存 / 复活 | 有保胎 12 vs 无保胎 5；0.95；复活 12 |
| 3 | 压缩后 | 关键事实 Recall | Δ0.000（不伤记忆） |
| 4 | 提炼 | 精确率 / 召回率 / F1 | 100% / 75% / 0.857（称呼规则补后） |
| 5 | 成本 | 注入 tokens / 延迟 / 日成本 | 1148/次（省 83%）、1.5ms 检索、~0.23 元/天 |

**方法论教训**：对照组必须彻底禁用被测机制（protect.enabled 开关）；时间尺度要匹配机制寿命（保胎 180 天别测 2.5 年）；LLM 当裁判有波动（需多次/人工复核）；测试材料有快照滞后性。
